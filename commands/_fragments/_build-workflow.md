# Build/Test/Format Workflow Fragment

**DO NOT INVOKE THIS FRAGMENT DIRECTLY.** This fragment is referenced by commands that need to build, test, or format code.

## Purpose

This fragment provides the standard workflow for:
- Running format commands
- Running test commands
- Handling module-specific vs. root builds
- Running full reactor builds (Maven)
- Checking for regenerated artifacts

## Instructions

### Step 1: Read Build Configuration

From the project's `project-standards.md`, extract:
- **Build tool** (Maven, Gradle, Go, yarn, npm, Cargo, none)
- **Build command** (e.g., `mvn verify`, `./gradlew build`)
- **Test command** (e.g., `mvn verify`, `./gradlew test`)
- **Format command** (e.g., `mvn verify`, `cd <module> && mvn -DskipTests install`)
- **Module-specific build** (yes/no)
- **Code style restrictions** (e.g., no Records/Lombok, no public API changes)

### Step 2: Determine Build Location

**For module-specific builds (e.g., camel-core, hawtio, forage):**
- Run format and test commands in the **module directory** where changes occurred
- Example: If you modified `core/camel-base/src/main/java/Foo.java`, run commands in `core/camel-base/`

**For root builds (most projects):**
- Run all commands from the **repository root**

**For projects with no build tool (e.g., ai-agents-oss-helper):**
- Skip build/test steps entirely

### Step 3: Run Format Command

Execute the format command from `project-standards.md`:

```bash
# Module-specific build example (camel-core)
cd core/camel-base && mvn -DskipTests install

# Root build example (most projects)
mvn verify
```

**Note:** Some projects auto-format during build (e.g., wanaku, camel-integration-capability). For these, the format command is the same as the build command.

### Step 4: Run Test Command

Execute the test command from `project-standards.md`:

```bash
# Module-specific build example
cd core/camel-base && mvn verify

# Root build example
mvn verify
```

**Skip this step if:**
- Project has no build tool (documentation-only projects)
- Changes are documentation-only (no code modified)

### Step 5: Check for Regenerated Artifacts

After running format/test commands, check if any files were regenerated:

```bash
git status
```

**If files were modified or created:**
- These are auto-generated artifacts (e.g., catalogs, DSL factories, metadata mirrors, schemas)
- Include them in your commit
- Do NOT manually edit these files

**Common regenerated artifacts:**
- `catalog/camel-catalog/src/generated/resources/` (Camel)
- `dsl/camel-*-dsl/src/generated/` (Camel)
- `tooling/maven/camel-package-maven-plugin/src/main/resources/` (Camel)
- `package-lock.json`, `yarn.lock` (JavaScript projects)

### Step 6: Full Reactor Build (Maven Projects Only)

**MANDATORY before committing** for Maven projects with code changes.

This step catches:
- Cross-module breakage that module-only builds miss
- Downstream code generation (catalogs, DSL factories, metadata mirrors)
- Integration issues between modules

**Before running, ask the user** which build mode to use:

> Which build mode would you like to use for the full reactor build?
> 
> **(a) Skip tests** (faster, recommended when step 4 already ran tests)
> - Command: `mvn clean install -DskipTests`
> - Use when: You already ran tests in step 4 and just need to verify cross-module compilation
> 
> **(b) Run full tests** (slower, catches cross-module integration regressions)
> - Command: `mvn clean install`
> - Use when: You want comprehensive validation including integration tests

**Wait for user's choice.** Do NOT pick a default silently.

**Then run the chosen command from the repository root:**

```bash
# Option (a) - Skip tests
mvn clean install -DskipTests

# Option (b) - Full tests
mvn clean install
```

**Critical:** This is a **full reactor build**. Do NOT add `-pl` or `-am` flags. A scoped build only covers the changed module and its upstream dependencies, leaving downstream generators stale. CI runs the full reactor build and then fails on any uncommitted regen artifacts, so the local check must match.

**If the build fails:**
- Fix the issue
- Re-run the build
- Do NOT commit on a failing root build

**Skip this step if:**
- Project is not Maven-based
- Changes are documentation-only
- Project has no build tool

### Step 7: Final Git Status Check

After the full reactor build, check for any new regenerated artifacts:

```bash
git status
```

**If new files were created or modified:**
- Add them to your commit
- These are downstream artifacts generated by the full build

## Build Tool Reference

| Build Tool | Format Command | Test Command | Full Build (skip tests) | Full Build (with tests) |
|------------|----------------|--------------|-------------------------|-------------------------|
| Maven | `mvn verify` or `cd <module> && mvn -DskipTests install` | `mvn verify` | `mvn clean install -DskipTests` | `mvn clean install` |
| Gradle | `./gradlew build` | `./gradlew test` | `./gradlew build -x test` | `./gradlew build` |
| Go (make) | `gofmt -w .` | `make test` | `make build` | `make test` |
| yarn | `yarn format` | `yarn test` | `yarn build` | `yarn build && yarn test` |
| npm | `npm run format` | `npm test` | `npm run build` | `npm run build && npm test` |
| Cargo | `cargo fmt` | `cargo test` | `cargo build` | `cargo test` |
| none | skip | skip | skip | skip |

## Command-Specific Notes

### For oss-fix-issue, oss-fix-backlog-task
- Always run full workflow (steps 1-7)
- Full reactor build is MANDATORY before commit

### For oss-quick-fix
- Run full workflow for code changes
- Skip build steps for documentation-only changes
- Full reactor build is MANDATORY before commit (code changes only)

### For oss-fix-ci-errors
- Always run full workflow
- Pay special attention to regenerated artifacts (often the cause of CI failures)
- Full reactor build is MANDATORY before commit

### For oss-address-review
- Run full workflow
- Full reactor build is MANDATORY before commit (Maven only)

### For oss-backport-pr
- Run full workflow after applying backport
- Full reactor build is MANDATORY before commit (Maven only)

### For oss-fix-sonarcloud
- Run format/test in module directory (per-module commits)
- Full reactor build is MANDATORY before push (after all per-module commits)

### For oss-fix-github-alert
- Run full workflow
- Full reactor build is MANDATORY before commit (Maven only)

## Error Handling

### Build Failures
- Read the error message carefully
- Check if it's a compilation error, test failure, or formatting issue
- Fix the issue and re-run the build
- Do NOT commit on a failing build

### Test Failures
- Investigate the failing test
- Determine if it's a legitimate failure or a flaky test
- Fix the code or update the test as appropriate
- Re-run tests to verify the fix

### Format Failures
- Some projects enforce strict formatting (e.g., Error Prone, Checkstyle)
- Run the format command to auto-fix issues
- If auto-fix doesn't work, manually fix the formatting issues
- Re-run the format command to verify

## Best Practices

1. **Always run format before test** - Formatting can change code behavior in rare cases
2. **Check git status after each build** - Catch regenerated artifacts early
3. **Run full reactor build before commit** - Catch cross-module issues locally
4. **Don't skip tests without justification** - Tests catch regressions
5. **Respect module-specific build requirements** - Some projects require it for performance
6. **Include regenerated artifacts in commits** - They're part of the change
7. **Wait for user input on build mode** - Don't assume what the user wants
